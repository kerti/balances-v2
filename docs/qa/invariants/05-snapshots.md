# Zone: SNAPSHOTS

The valuation substrate beneath FINANCE. Every net-worth number the report engine
derives traces back to a position **snapshot** — the dated value record of
ADR-0006. FINANCE and LIFECYCLE both *assume* a snapshot's rules on read
(INV-FINANCE-03's "latest snapshot ≤ M", INV-LIFECYCLE-03/04's 0-value close);
this zone guards them at the write/storage layer where they are actually enforced.
The cut here is **temporal/value** correctness — a snapshot's date pinned to its
month, a correction superseding (not double-counting) the prior value, a deleted
reading staying out of every read. Cross-household isolation is INV-TENANCY-01/-06,
not repeated here. Code lives in the snapshot write paths of `internal/repo/`
(`snapshot_as_of_month`, `import_snapshots.go`) and the handler validation in
`internal/assets/snapshots.go` / `internal/investments/snapshots.go`; the
constraints themselves are migration 00003 plus the per-table partial unique index.

A snapshot's date is allowed to *precede* its position's creation — historical
backfill (a 2026 account importing 2015 readings) is intentional, so there is no
"date ≥ creation" invariant here.

| ID | Invariant | Source | Severity |
|----|-----------|--------|----------|
| INV-SNAPSHOTS-01 | A snapshot's `as_of_date` is pinned to its `year_month` month — the `<table>_as_of_in_month` CHECK (migration 00003) fires on insert and update across all four snapshot tables; an out-of-month date is `ErrSnapshotDateOutsideMonth` (400), a NULL or in-month date passes | ADR-0006 | High |
| INV-SNAPSHOTS-02 | At most one live snapshot per (position, year_month) — the unique index is partial (`WHERE deleted_at IS NULL`), so a soft-deleted row is superseded by a fresh re-record of the same month as a genuinely new row, not a resurrection (#57); creating a second snapshot while the first is still live hits the same index and is mapped to the informative `ErrSnapshotMonthExists` (409), not a generic 500 (#395). Since Record snapshot (#788, INV-SNAPSHOTS-12) the 409 is only a guard against a stale tab or a double submit: the dialog replaces a recorded month instead of POSTing it, and a replace leaves the month's POST still refused | ADR-0006, ADR-0007 | High |
| INV-SNAPSHOTS-03 | A soft-deleted snapshot is excluded from every value read — the live list, the latest-per-position selection, and the report-feeding query all carry `deleted_at IS NULL`, so a corrected or removed reading never re-enters net worth | ADR-0007 | Critical |
| INV-SNAPSHOTS-04 | Bulk import is keyed by (position, year_month): a month whose values differ is replaced (the earlier row archived, INV-SNAPSHOTS-11) rather than double-counted, an identical month is skipped, dry-run writes nothing, and the whole batch is one transaction | ADR-0006 | High |
| INV-SNAPSHOTS-05 | A snapshot is a past observation — a future `year_month` (`CodeFutureYearMonth`) or future `as_of_date` (`CodeSnapshotFutureDate`) is rejected 400 on both the create and update paths. The check (shared `dateguard.IsFuture`/`IsFutureMonth`, used by all four snapshot tables **and** investment transaction dates) tolerates the maximum forward timezone offset (UTC+14 → one civil day ahead of UTC) so a UTC+ member's local "today", which can be UTC-tomorrow, is not falsely rejected (#426); only a date/month more than one civil day past UTC today is "future". Verified in `dateguard_test.go` (pure boundary) | ADR-0006 | Medium |
| INV-SNAPSHOTS-06 | Bulk monthly-entry save is dirty-rows-only, atomic, and month-aware — uniformly across every group: the amount-only groups (Asset/Liability/Receivable, #421→#422), the qty×price Investment group (Stock/MutualFund/Gold, #423), and the accrued Investment group (Bond/TimeDeposit, #424). The caller sends only changed rows; every row is validated for month-aware eligibility (owned, not deleted, active or terminated in the target month or later) before any write, and any ineligible row aborts the whole batch (nothing written) returning a per-row error keyed by position; eligible rows go through the replace path (INV-SNAPSHOTS-11) so re-entry archives the earlier value rather than duplicating or overwriting it, and the response tallies written / replaced / unchanged; there is deliberately no `created_at` guard (would break backfill/onboarding) | ADR-0046 | High |
| INV-SNAPSHOTS-07 | The bulk monthly-entry list surfaces every eligible position with its carry-forward prefill — the most-recent snapshot at or before the target month (null when the position has no history yet), the position's native currency, and the month it was carried from — excluding positions terminated before the target month. Holds for every group: the amount-only groups (Asset/Liability/Receivable — a flat group with no subtype, Receivable, returns an empty subtype and renders one ungrouped list), the qty×price Investment group (whose prefill carries the last quantity + price per unit, #423), and the accrued Investment group (whose prefill carries the last total value + accrued interest, plus each bond's coupon disposition, #424) | ADR-0046 | Medium |
| INV-SNAPSHOTS-08 | The qty×price bulk monthly-entry (Stock/MutualFund/Gold, #423) carries two tab-stops per row (quantity, price per unit) and derives the stored `amount` server-side as quantity × price_per_unit, writing the qty×price branch of `investment_snapshot_shape` (quantity + price_per_unit set, accrued_interest null); eligibility is filtered to exactly the three qty×price subtypes, so a bond/time_deposit (accrued shape) can never be written or listed through this path | ADR-0046 | High |
| INV-SNAPSHOTS-09 | The accrued bulk monthly-entry (Bond/TimeDeposit, #424) carries two directly-entered tab-stops per row (total value → stored `amount`; accrued interest → `accrued_interest`), writing the accrued branch of `investment_snapshot_shape` (accrued_interest set, quantity/price_per_unit null) with no server-side derivation; the per-row accrued default follows coupon disposition (an `accrues` bond forces a real entry, pays-out bonds and time deposits default to 0); eligibility is filtered to exactly the two accrued subtypes (so a qty×price investment can never be written or listed through this path) and a time deposit is further confined to its term window (placement month..maturity month, #62) — an out-of-term month excludes it from the list and rejects a write row | ADR-0046 | High |
| INV-SNAPSHOTS-10 | A bulk monthly-entry prefill is shown rounded but saved as stored — an untouched row is never re-saved with a rounded value. A carried-forward **money** field (an amount, accrued interest) displays at the currency's minor units (`1408210.1634` reads `1,408,210.16` for IDR; JPY/KRW/VND whole units) while a **quantity** or **price per unit** shows every stored place. The display string is never the dirty-check baseline: `isDirty` and the save body read the stored value, so an untouched row stays out of the payload (Save disabled, nothing POSTed), and an untouched sibling field on an edited row is sent as stored (unrounded), while a field the user typed in is sent as the canonical decimal string they entered. Verified in `EntryScreen.minorUnits.test.tsx` and `shapes.test.ts` | ADR-0046 / ADR-0056 / #784 | High |
| INV-SNAPSHOTS-11 | Replacing a snapshot archives, never overwrites. Every write that changes the values of an existing month (Edit `PATCH`, which is also Record snapshot's replace, bulk save, import) soft-deletes the live row and inserts the new values in **one transaction**, for all four snapshot groups and all three shapes (amount-only, quantity+price, accrued): afterwards the month has exactly one live row holding the new values and the displaced row survives as an ordinary soft-deleted row. `supersedes` stays **null** on both (it keeps its one meaning, "a close row displaced this", ADR-0052 §2), so a compacted backup does not carry the displaced row. A row whose fields (amount, currency, quantity / price per unit / accrued interest where the shape has them, as-of date, note) all equal the live row's, compared as decimals, is **unchanged** and writes nothing; re-importing identical data creates no archived rows. A failure midway leaves nothing changed, a soft-deleted month is inserted rather than replaced, another household's row is rejected untouched, and the single-write response names the displaced row (`replaced_id`, null when nothing was replaced) while bulk responses tally `replaced` and `unchanged`. The month's report still regenerates, since the watermark counts archived rows | ADR-0058 §1, ADR-0052 §2 | Critical |
| INV-SNAPSHOTS-12 | Record snapshot follows one overwrite rule on all three snapshot shapes (amount-only, quantity × price, accrued interest). The dialog opens on the month after the latest snapshot, capped at the current month, with the value fields **empty**; an empty month offers a muted "Last recorded" line and **Same as last month**, which fills only the value fields (amount, or quantity × price, or total + accrued) from the latest earlier snapshot and **never the statement date**. A month that already has a snapshot (the default month when the current one is recorded, or one picked) switches the dialog to **replace mode** before anything is sent: a notice names the month and its existing value, the fields are prefilled from it, and Save goes through the update (`PATCH`) path so the earlier value is archived (INV-SNAPSHOTS-11) and the single toast offers Undo through the replace-undo route (INV-SOFT-DELETE-09); the create `POST` is not called for a recorded month. Moving from a replaced month to an empty one drops the prefilled values. Verified in `CreateSnapshotDialog.test.tsx`, `RecordSnapshotShapes.test.tsx` and `RecordSnapshotReplace.test.tsx`, with the server-side guard in `snapshot_month_exists_test.go` | ADR-0046 amendment, ADR-0058 §1-§2, #788 | High |
| INV-SNAPSHOTS-13 | A snapshot's statement date (`as_of_date`) is never invented. Bulk monthly entry starts the date **blank** (no end-of-month seed, and no per-user preference to seed from: `users.carryover_date_mode` was dropped), a month change clears a date picked for the old month rather than re-seeding one, and every snapshot dialog starts blank too. A save that carries no date (key absent, `null`, or the empty string a cleared date input sends) stores `as_of_date = NULL`; a date the user picks is stored as picked and stays bound to the snapshot's month (the in-month CHECK, INV-SNAPSHOTS-01). Nothing computes from the date, so a blank one never changes a figure. Verified in `EntryScreen.statementDate.test.tsx` (blank, sent as null, picked, cleared on month change) and, against a raw `as_of_date` read, `statement_date_test.go` (bulk and single create) | ADR-0046 amendment, #790 | High |
