# Zone: PRESENTATION

The first **frontend-native** zone: the **client presentation + input-guardrail
layer** the non-technical audience actually touches (ADR-0021). It catalogues the
pure functions in `frontend/src/lib` that render the backend's truth without
lying to a household member, and the form-side guards that stop bad input before
it round-trips into an opaque API error. The zone **mirrors, never re-owns, the
backend truth** — FINANCE owns the net-worth number, SNAPSHOTS owns the
server-side future-date CHECK, EXPORT owns the joint-privacy rule; the rows here
pin the *client twin* of each, cross-linked, never a clone. A client-side render
or guard failing does not corrupt stored data, but it *misinforms or mis-guards*
the one reader who can't tell a display bug from a real number — which is the bar
for a row here (silent corruption or a leaked/false number, not mere mechanics).
The later rows (04+) extend the zone from pure `lib` helpers to the **component
tier** — the descriptor-driven list core (ADR-0043), verified by RTL+MSW+jsdom
suites that activate ADR-0021's deferred component tests (#69). Every row here is
verified by a vitest suite that runs in the same per-PR gate it's credited in
(`how-it-works.md`), so there is no `-strict` hazard. Source:
ADR-0021 (non-technical audience), ADR-0026 (i18n/locale). A later **E2E-native**
extension (flows a unit test can't reach, e.g. the OAuth round-trip, ADR-0024) is
seeded separately once these vitest rows land, since Playwright is subject to the
`@smoke`/nightly gate wrinkle.

What the primitives cannot reach is hand-floored: the three `SettingsScreen` `<select>`s (at the time there was **no `ui/select.tsx`** — all 34 `<select>` callsites hand-rolled `h-9`, 28 of them dialogs, so a shared select primitive was deferred to #541, which added it), the checkbox/radio hit rows in `SettingsScreen` / `BackupPanel` / `RestorePanel`, and the three Settings text links. The floor's last hidden hole was not a missed callsite but a **wrong engine** (#572): `h-8` / `max-md:min-h-11` on `Input` are only a promise the platform has to keep, and for the temporal input types iOS Safari does not keep it — it draws a **native control that holds its own intrinsic width and height**, so on a real iPhone the Entry screen's `grid-cols-2 items-end` row rendered the `type="date"` field taller than its `type="month"` sibling (bottom-aligning the cells, which visibly dropped the "Month" label out of line) and overflowing its column into the `gap-3`, the two reading as one continuous bar. All 39 `type="date"` / `type="month"` callsites across 30 files go through the primitive, so the reset lands once — `appearance-none`, scoped to the five temporal types (`date` / `month` / `week` / `time` / `datetime-local`, the last three unused today) rather than applied to every input, because on `type="file"` it would strip the platform's Choose-file button that the primitive's `file:*` classes style rather than replace. The outer `appearance` was the whole gap: Tailwind's preflight already normalises the WebKit shadow parts *inside* the control (`::-webkit-date-and-time-value` gets `min-height: 1lh` + `text-align: inherit`, `::-webkit-datetime-edit` an unpadded inline-flex), but preflight touches `appearance` for no input type. This row's own history is the lesson: #541 explicitly measured these fields as fitting "in full at ~157px" and cleared them, in **Chrome DevTools device mode** — which emulates viewport, DPR, touch and UA string but still renders with Blink and Chrome's own form controls, leaving every platform-owned thing (form widgets, native pickers, font fallback, dvh, safe-area) untested — so a mobile finding taken there is not evidence about a phone. Playwright cannot close that gap either: a `webkit` project runs WebKit's *desktop* form controls, not iOS's UIKit-backed ones, so the pixel truth for the temporal types is a real-device check and the suite pins the class contract only. The same real-device pass found two more of the same shape. **`<select>` had the identical native-metrics problem** — the control was the right width but visibly shorter than the text field beside it, because iOS honours a select's width and ignores its height while the platform appearance is intact — which means #541's floor never actually held there either; the reset is the only way the height lands and it takes the platform arrow with it, so **#541's deliberate "keep the native arrow" decision is reversed** and the app draws its own chevron (`--select-chevron` in `index.css`, themed per mode, lucide's `chevron-down` path so it matches the icon set, delivered as a background image because a `<select>` can host neither child markup nor a pseudo-element, with `pr-8` reserving its room). #541's actual *goal* survives the reversal untouched: a native `<select>` still opens iOS's native sheet or wheel on tap regardless of appearance — what the platform draws in the page and what it opens over the page are independent — so only the in-page arrow changed. **Pagination was simply missed by the whole B-series**: `PaginationControls` rendered one link per page unconditionally, so the control's width grew with the data and a long history ran its last pages and the Next arrow off the right edge of a phone, unreachable, while the `PaginationEllipsis` primitive to prevent it sat unused since the control was written. It now renders a window (`lib/pageWindow.ts`) of **constant item count** (`siblings * 2 + 5`, so paging never resizes the control or reflows its neighbours — near the ends the run of numbers extends into the slot the absent ellipsis would have held, and a gap covering exactly one page spells that page out rather than hiding nothing behind an ellipsis that costs the same slot), with first and last always one tap away, and `siblings` chosen by width alone: 0 below 768px where seven floored items is all 390px holds, 1 above. Its tap targets were also below the floor, for the documented reason that `size="icon"` is the one `Button` family #559 skips — so a page number carries `max-md:size-11` in the primitive rather than at the two callsites (Income list, every detail-page history section), the non-interactive ellipsis matches it so a 32px item doesn't read as a misalignment in a 44px row, and prev/next take `max-sm:w-11` — `sm` not `md`, because their labels are `hidden sm:block`, so they are icon-only *below 640px* (where Button's height-only floor left them 44×34) and text buttons above it that a 44px width cap would squash. The same pass then found the floor's premise failing outright on the **row action menus**: the ⋮ on every card was **completely dead on iOS Safari** — not mispositioned, not opening-then-closing, the content never mounted — because Radix's menu trigger opens on `pointerdown` or the Enter/Space/ArrowDown keys and has **no `click` path at all**, and mobile WebKit was not delivering a usable `pointerdown` to that button. The discriminator that identified it: the same phone opens every Create/Edit dialog fine, and Radix's *dialog* trigger opens on `click` — so `click` arrives, `pointerdown` does not, and the four row menus were the only thing in the app depending on the event iOS withholds. `useMenuOpenOnClick` (in `ui/dropdown-menu.tsx`, used by `RowActionsMenu` / `IncomeRowMenu` / `SnapshotRowMenu` / `TransactionRowMenu`) adds the missing path as a **controlled root plus a click handler that opens only when the menu is closed**, so wherever `pointerdown` already worked Radix has set `open` before the click lands and the fallback self-cancels; no `preventDefault`, so Radix's own path and the keyboard affordances are untouched. It also carries `modal: false`, since none of these menus has a claim to modality (no focus trap, no need to freeze the page) while Radix's default `modal` engages react-remove-scroll's body scroll lock plus `pointer-events: none` on `<body>` — free on desktop WebKit, treacherous in mobile WebKit, which ignores `overflow: hidden` on body for touch scrolling. Unlike the platform-metrics rows above, this one is **not** a class-contract stand-in: dispatching a bare `click` with no `pointerdown` is exactly what the phone was doing, so jsdom reproduces the failure and the guard is a real regression test (reverting the hook turns it red). The floor itself then had to reach **what the trigger opens**, which no sweep had touched: `py-1` + `text-sm` is a ~28px row, so the menu that a floored `size-11` trigger exists to reach handed a phone two under-floor targets. `max-md:min-h-11` now sits on every interactive item kind in the primitive (`DropdownMenuItem`, `CheckboxItem`, `RadioItem`, `SubTrigger`); the non-interactive parts (`Label`, `Separator`, `Shortcut`) stay dense on purpose, since they are not targets and padding them only makes the menu taller. Last, **truncated select labels in the narrow dialog shell**: a `grid-cols-2` row inside `DialogContent` (`sm:max-w-sm`, so ~170px per column at *every* width — there is no wider layout to fall back to, which is why these stack unconditionally rather than under a `md:` divergence) leaves ~128px of text after the field's padding and the new chevron's `pr-8`, about 18 characters. Five callsites overran it and now hold a full-width row each: income **category** (`CreateIncomeDialog` + `EditIncomeDialog`, whose date field goes full-width with it, and which must agree since a member picks a category on create and re-reads it on edit), **bond type** (`CreateBondDialog` — `EditBondDialog` already had it full-width, so the two now agree; the **currency** field that shared the row does not follow it to full width but moves beside the **face value** it denominates, at the same `grid-cols-[1fr_120px]` split the income dialog uses for amount+currency, with the **placement date** dropping to its own row below the pair — three characters do not earn a full row. Full width rather than a tighter split is deliberate: it is the only version that survives a locale with longer wording than EN/ID.
